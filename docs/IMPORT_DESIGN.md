# Non-executing metrics import (0.1.2)

## Value and limits

The previous `run` interface required a Python entry script, which was unnecessary friction for an existing DVC pipeline. `import-metrics` is a separate path that reads existing JSON metrics and adds a declared numerical contract without rerunning or modifying that pipeline. This also permits metrics produced by R/Julia/native tools, provided the user supplies JSON; it does not claim support for executing those languages.

The implementation imports no project module, calls no shell/process API, reads no Git configuration or credentials, and makes no network request. A regression patches `subprocess.run` to fail if called and checks source bytes remain unchanged. Existing source files may still receive filesystem access-time updates from being read.

## Trust boundary

Contract schema 1 of kind `metric-contract` permits only title, source, claims and schema/kind fields. Commands and execution options are rejected. The source string is a user-authored label, not authenticated provenance.

Receipt schema 2 deliberately differs from execution receipts: it has `evidence_mode: imported`, `executed: false`, no `exit_code` and no claimed experiment environment. Verification rejects execution fields. `supported` means the imported values match the numerical claims, not that execution occurred or the source is recent. The report labels the boundary prominently.

The exact source-byte snapshot, selected-object metrics, contract and claim results are included. File size is limited to 2 MB at parsing. JSON Pointer selection is explicit and limited to object keys, with no revision guessing. Verify checks artifact hashes, re-extracts from the original snapshot, verifies the deterministic normalized metrics, and recalculates claim outcomes. A changed normalized output cannot pass merely by updating its own hash without also matching the selected source.

Unsigned bundles remain forgeable as a whole. No public upload or secret redaction happens automatically. Non-executing import is not a sandbox for the separate `run` command.

## Actual verification

Both direct metrics and nested JSON exported by real DVC 3.67.1 were imported and verified locally. Both returned `supported / imported / executed=false`. The numeric values were previously generated by actual DVC runs; no new scientific execution is implied. The import tests cover negative/missing/null values, selection, duplicate keys, size limits, contract injection, source and normalized-artifact tampering, read-only source preservation and execution-field rejection.

This demonstrates compatibility and a non-executing workflow, not competitive superiority. DVC can still run arbitrary equivalent checkers; setup/review time and user error-rate advantages remain unmeasured. The final integrated 0.1.2 runtime subsequently passed historical six-matrix CI; see VALIDATION.md for precise scope.

## Audit repairs before release

Two independent reviews found and reproduced typed-comparison, FIFO-blocking and malformed/deep-JSON output issues. The revised implementation:

- compares claim JSON with type-preserving deterministic serialization, so numeric `1` cannot be replaced by JSON `true` (including legacy receipt checks);
- opens files nonblocking where supported, checks the opened descriptor is a regular file, and applies bounded reads; JSON is at most 2 MB and evidence hashing at most 64 MiB per file;
- rejects JSON deeper than 64 levels and invalid Unicode surrogates, translating parser/serialization recursion errors to a controlled `Invalid` result;
- serializes and validates all imported outputs before creating the destination. Data-format errors leave no half-bundle. Filesystem failures such as full disk can still leave partial output; the receipt is written last and must verify before completion is claimed.

61 local tests pass, including subprocess-timeout-guarded FIFO regressions on POSIX. FIFO tests are intentionally skipped on systems without `os.mkfifo`; a skipped test is not evidence about Windows named pipes. This revision requires independent re-review and new CI before acceptance.

## Private creation of new imports

New import output directories and any missing parent directories are created
with POSIX mode 0700, and each evidence file is created exclusively with mode
0600 before any source bytes are written. The process umask is not changed.
Existing outputs (including dangling symlinks) are rejected; existing parents
are never chmodded. POSIX writes are anchored to the opened output directory
and use exclusive, no-follow creation. Concurrent imports to one destination
cannot merge bundles: a loser fails without modifying the winner's files.

Choose a trusted parent directory. This is not protection against another
process running as the same user, hostile filesystem implementations, or an
administrator. On Windows, these mode arguments do **not** establish a private
ACL: files inherit the destination's permissions. Use an already private
Windows folder; no ACL or system security setting is changed. Windows ACL
isolation and adversarial directory replacement are not claimed or tested.

The full original metrics snapshot is still retained without redaction.
Failures may leave a private partial directory; no rollback or automatic
recursive deletion is attempted. The receipt is written last, but interrupted
receipt writes can themselves be partial, so completion must be checked with
`verify`, not inferred merely from a filename's presence. Existing historical
bundles remain readable and are not modified by this change. This change is
specific to `import-metrics`, not a privacy guarantee for the separate runner.
